## Summary

A user who may switch themes creates a temporary link that shows the site's front end in one of their permitted themes, in a browser where nobody is logged in. A typical use is cross-browser testing in BrowserStack, where signing in on every device is slow.

The link is protected by:

- a separate access key
- an expiry time
- a limited number of uses (single-use by default)
- lockout after wrong keys

It grants **only a theme view**. It never logs anyone in.

## Current state, required state, gap

- **Current:** `Theme_Switcher::determine_theme()` returns `null` when `wp_get_current_user()` doesn't exist, so logged-out visitors always see the site theme. Previews (`Preview`) need a logged-in user and a nonce bound to that user.
- **Required:** an anonymous browser shows a chosen theme after a valid link and key, until the link's expiry, without any login.
- **Gap:**
    - link and session storage
    - a key form
    - an anonymous resolution branch
    - cookie handling
    - admin and user screens
    - cleanup
    - privacy hooks
    - cache safety (TTF010)

## Principles

1. **Theme view only.** The visitor stays anonymous: no user is set, no auth cookie, no capabilities. Testing logged-in pages needs a separate low-privilege test account in BrowserStack, not this feature.
2. **Front end only.** Never in wp-admin, the Customizer, the excluded admin pages, or REST/AJAX that classify as `admin` or `none`.
3. **The global theme never changes** (invariant 1). The same `template` / `stylesheet` filters apply the theme.
4. **A link is a request for a theme, not a permission.** On every request, the creator's current permissions decide.
5. **Off by default.** An admin enables the feature and picks the roles that may create links.

## User stories and acceptance criteria

### Creating

1. As an eligible user in a role allowed to share, I see "Shareable preview links" in Personal Theme Settings.
2. I pick:
    - a theme, from my permitted themes
    - an expiry: default 1 hour, at most the admin maximum
    - a number of uses: default 1, at most the admin maximum
    - a key: generated by default, or my own of at least 8 characters
3. After creating, I see the link and the key **once**, each with a copy button, and the advice "Send the key separately from the link."
4. I see my links with status, uses left, expiry and failed attempts, and can revoke any of them.
5. In the ThemeToggle toolbar menu (TTF001), "Share this page…" opens the create form pre-filled with:
    - the theme I'm viewing, if I may share it; otherwise my first shareable theme
    - the current front-end page as the link's path (the home page when I'm in wp-admin)
    - the default expiry and number of uses
6. "My preview links (N active)" in the same menu opens my list of links. N counts my active links.
7. The toolbar never creates a link by itself: a link is only created when I submit the form.

### Opening

1. Opening the link always shows the same key form, whether the link is valid or not. It spends nothing.
2. A correct key spends one use, and the browser shows the site in that theme on every front-end page until the link expires.
3. A wrong key, an invalid link, an expired link and a locked link all give the same message: "Link or key is invalid or expired." A wrong key never spends a use.
4. After 5 wrong keys the link is locked, and the creator sees "Locked after failed attempts".
5. A visible bar says "Previewing: Astra Child · End preview". End preview returns the browser to the normal site.

### Managing

1. Admins see all links in a "Preview Links" settings tab and can revoke one or all.
2. Revoking ends open browser sessions at once.
3. Dead links (expired, used up, locked, revoked) are deleted after the retention period (default 30 days).

## Settings (new "Preview Links" tab)

| Key | Type | Default | Range / rule |
| --- | --- | --- | --- |
| `share_enabled` | bool | false | |

| `share_default_minutes` | int | 60 | 5 … `share_max_minutes` |
| `share_max_minutes` | int | 1440 (24 h) | 15 … 10080 (7 days) |
| `share_max_uses` | int | 10 | 1 … 50 |
| `share_require_key` | bool | true | |
| `share_max_active_per_user` | int | 5 | 1 … 20 |
| `share_retention_days` | int | 30 | 1 … 90 |

All go into `Settings::get_defaults()`, a new `TAB_KEYS['share']`, and `sanitize_value()` with clamping (skill recipe "Add a setting").

## Data model

Two custom tables, created with `dbDelta()` in `Installer` and versioned with `tt_db_version`. An upgrade check runs on `plugins_loaded` when the version differs. Options and transients can't do the atomic "spend one use" safely: options are rewritten whole, and a persistent object cache can drop transients at any time.

### `{$wpdb->prefix}tt_share_links`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED AUTO_INCREMENT | PK |
| `token_hash` | CHAR(64) | `hash_hmac( 'sha256', $token, wp_salt( 'auth' ) )`, UNIQUE |
| `key_hash` | VARCHAR(255) NULL | `wp_hash_password( normalised key )`; NULL when no key is required |
| `creator_id` | BIGINT UNSIGNED | indexed |
| `stylesheet` | VARCHAR(255) | |
| `created_at` | DATETIME | UTC |
| `expires_at` | DATETIME | UTC, indexed |
| `max_uses` | SMALLINT UNSIGNED | |
| `uses_left` | SMALLINT UNSIGNED | |
| `failed_attempts` | TINYINT UNSIGNED | |
| `status` | VARCHAR(12) | `active`, `revoked`, `locked`. "Expired" and "used up" are derived from `expires_at` and `uses_left`. |
| `last_used_at` | DATETIME NULL | |
| `ended_at` | DATETIME NULL | When it stopped working (revoked, locked, used up, expired); used for retention. |

### `{$wpdb->prefix}tt_share_sessions`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED AUTO_INCREMENT | PK |
| `session_hash` | CHAR(64) | SHA-256 of the cookie value, UNIQUE |
| `link_id` | BIGINT UNSIGNED | indexed |
| `created_at` | DATETIME | UTC |
| `expires_at` | DATETIME | ≤ the link's `expires_at` |

On multisite (TTF014) the tables are per site through `$wpdb->prefix`. The token, key and cookie value are never stored in plain text.

## Flow

### 1. Create

- `admin_post_tt_share_create`:
    1. `check_admin_referer( 'tt_share_create' )`
    2. logged in; feature on; user in `share_roles`; `can_user_select( $user, $stylesheet )`
    3. active links below `share_max_active_per_user`
    4. clamp minutes and uses to the settings
- **Token:** `bin2hex( random_bytes( 32 ) )` (256 bits).
- **Key:**
    - Generated: 10 characters from the 29 characters `23456789ABCDEFGHJKMNPQRSTWXYZ`, which leave out the look-alikes `0/O`, `1/I/L` and `U/V`. Shown in groups as `7KQ-M4XP-9TR`. Compared after removing spaces and dashes and upper-casing, since it is easy to mistype on phones.
    - Custom: at least 8 characters, at most 64. Compared exactly, with no normalising.
    - Stored as `wp_hash_password()`.
- **Showing once:** the plain link and key are put in a transient `tt_share_new_{user_id}` for 5 minutes and shown on the next page load, then the transient is deleted. **They are never put in a URL**, such as a redirect query string, where logs and history would keep them.
- **Link format:** `add_query_arg( 'tt_share', $token, home_url( '/' ) )`. The creator may add a site path; validate it with `wp_validate_redirect()` against the home URL.

### Toolbar entry points (with TTF001)

TTF018 registers a `share` section in TTF001's toolbar registry (`$toolbar->add_section( 'share', 20, … )`), so its items sit between "Switch theme" and "Why this theme?".

- **Conditions:** the section adds nothing unless the feature is on, the user is in `share_roles` and has at least one shareable theme (`get_selectable_themes()`).
- **"Share this page…"** (`themetoggle-share-create`) links to the create form:
    - `profile.php?tt_share_theme={slug}&tt_share_path={path}#tt-share-links`
    - `{slug}` is the theme applied to this request when the user may share it, otherwise empty.
    - `{path}` is the current request path (`Redirect::current_uri()`, which already strips preview arguments) on the front end, and `/` in wp-admin.
    - Opening it changes nothing: it is a GET that only fills in the form. No nonce is needed for that; the form's submit has its own (`tt_share_create`).
- **Why a form and not one click:** a toolbar item is a GET link. Creating on click would have to put the new key into the redirect URL or the toolbar, where history and logs keep it, and expiry, uses and the key are choices worth seeing each time.
- **Pre-fill values are suggestions, never trusted:**
    - `tt_share_theme` is read with `sanitize_text_field()` and used only if it is in the user's shareable themes; otherwise the select starts at the first shareable theme.
    - `tt_share_path` is reduced to a path (`wp_parse_url()`, path and query only, `tt_share` and preview arguments removed), then checked again with `wp_validate_redirect()` when the form is submitted.
    - Both are printed with `esc_attr()`.
- **"My preview links (N active)"** (`themetoggle-share-list`) links to `profile.php#tt-share-links`. N comes from one indexed `COUNT(*)` on `tt_share_links` for this creator with `status = 'active'` and `expires_at > NOW`, run only while the toolbar is showing and cached for the request. Leave the count out (just "My preview links") if it would cost more than that one query.
- **Share visitors** (logged out) never see the toolbar, so none of this reaches them.

### 2. Open (GET)

On `template_redirect`, early, if `$_GET['tt_share']` is present:

- Render the plugin's own minimal page with **no theme code**: no `get_header()`, no `wp_head()`. Plain HTML with the plugin's CSS file and a form. Theme code isn't involved, and the page is identical for valid and invalid tokens.
- Headers:
    - `nocache_headers()`
    - `Cache-Control: no-store, private`
    - `X-Robots-Tag: noindex, nofollow`
    - `Referrer-Policy: no-referrer`
    - `X-Frame-Options: DENY`
- Set a short-lived anti-CSRF cookie `wp-themetoggle-share-form` holding 32 random bytes in hex: `HttpOnly`, `Secure` when `is_ssl()`, `SameSite=Strict`, 15 minutes. Put the same value in a hidden field.
- **Nothing is read from the database** on GET, so link scanners, chat unfurlers (Slack, Teams, WhatsApp) and browser prefetching can't spend, lock or probe a link.

### 3. Submit the key (POST)

The form posts to `admin-post.php?action=tt_share_open`, handled by an `admin_post_nopriv_` handler. Admin-post requests classify by referer; this one sets no theme anyway. Checks, in this order:

1. **Anti-CSRF:** the cookie value equals the hidden field (`hash_equals()`). WordPress nonces are not used: every logged-out visitor shares user ID 0, so they protect nothing here.
2. **Rate limit per IP:** at most 10 failed attempts per 15 minutes, counted in a transient keyed by `hash_hmac( 'sha256', $ip, wp_salt() )`. Over the limit, show the generic message and stop.
3. **Feature enabled.**
4. **Token lookup:** by `token_hash`. If no row matches, run `wp_check_password()` against a fixed dummy hash, so response time doesn't reveal whether the token exists.
5. **Link state:** `status = 'active'`, `expires_at > UTC_NOW`, `uses_left > 0`.
6. **Key:** `wp_check_password( normalised input, key_hash )`, when a key is required.
    - Wrong key: `UPDATE … SET failed_attempts = failed_attempts + 1`, and `status = 'locked', ended_at = NOW` when it reaches 5. Count an IP failure; show the generic message.
7. **Creator and theme:** the creator still exists, is still in `share_roles`, and `can_user_select( $creator, $stylesheet )` is still true. The theme is installed and error-free.
8. **Spend one use atomically:**

    ```sql
    UPDATE {prefix}tt_share_links
    SET uses_left = uses_left - 1, last_used_at = %s,
        ended_at = IF( uses_left = 1, %s, ended_at )
    WHERE id = %d AND status = 'active' AND uses_left > 0 AND expires_at > %s
    ```

    Granted only if `$wpdb->rows_affected === 1`. Two submits at the same moment can't both succeed. Check that `IF()` works on the SQLite integration used by e2e; if not, set `ended_at` in a second statement.
9. **Session:** cookie value `bin2hex( random_bytes( 32 ) )`; insert `session_hash = hash( 'sha256', value )` with `expires_at` = the link's expiry.
10. **Cookie** `wp-themetoggle-share`: `HttpOnly`, `Secure` when `is_ssl()`, `SameSite=Lax`, `path = COOKIEPATH`, `expires` = the link's expiry. The `wp-` prefix matches common "bypass cache" cookie patterns (for example Cloudflare APO and many Nginx configs); TTF010 must confirm this for each cache.
11. **Redirect:** 303 to the link's path **without** `tt_share` (`remove_query_arg()`, `wp_safe_redirect()`). Clear the form cookie.

Every failure in steps 3–7 shows the same message and the same form, with HTTP 200.

### 4. Browse (every request with the cookie)

- **New branch in `Theme_Switcher::determine_theme()`**, before the login check: the user isn't logged in, the context is `frontend`, and the share cookie is present → ask a new `Share_Session` service. Logged-in users ignore the cookie and keep their own rules.
- **`Share_Session::get_theme()`:** one query joining `tt_share_sessions` to `tt_share_links` by `session_hash`, cached for the request. All must be true:
    1. session not expired
    2. link `status = 'active'` (revoked or locked links end their sessions at once)
    3. link not expired (`uses_left` doesn't matter here: the use was spent on entry)
    4. feature enabled
    5. creator exists and is still allowed to share
    6. `can_user_select( $creator, $stylesheet )`

    Then the theme goes through the normal validation in `Theme_Switcher::get_applied_theme()` (installed, `errors()` empty, not the site theme, context not `none`).
- **On any failure:** the default theme; expire the cookie; no message.
- **Headers on every response with a share theme:** `send_private_cache_headers()` plus all TTF010 signals, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`.
- **`Data_Guard`** is active (it activates whenever a theme is applied).
- **Preview bar:** "Previewing: {theme name} · End preview". End preview is an `admin_post_nopriv_tt_share_end` POST, protected the same way as the key form. It deletes the session row and expires the cookie. Don't show the creator's name or anything else about them.

### 5. Revoke, expire, clean up

- **Revoke:** `admin_post_tt_share_revoke` (nonce, and creator or `manage_options`) sets `status = 'revoked', ended_at = NOW` and deletes the link's sessions.
- **Revoke all:** for the creator (own links) or admins (every link), with a confirmation checkbox like Reset All.
- **Daily cleanup** (`wp_schedule_event`, hook `themetoggle_share_cleanup`):
    - delete links whose `ended_at`, or `expires_at` for links that expired without being marked, is older than `share_retention_days`
    - delete sessions past `expires_at`
    - work in chunks of 1,000
- **Expiry never depends on cleanup:** WP-Cron only runs when the site has visitors. Every check above compares `expires_at` itself.
- **Deactivation:** unschedule the cron. Add a `register_deactivation_hook()`; the plugin has none today.
- **User deleted** (`delete_user` / `deleted_user`): delete their links and sessions.
- **Uninstall:** drop both tables and delete `tt_db_version` and the cron event (`uninstall.php`).

## Rate limiting

- The visitor's IP is `$_SERVER['REMOTE_ADDR']` only. Proxy headers (`X-Forwarded-For`) are trusted only when an admin names one in `share_trust_proxy_header`. Otherwise anyone could fake a new IP per attempt and get around the limit.
- The per-IP limit uses transients, which is acceptable for a best-effort limit. The per-link lock (5 failures, in the table) is the hard limit and doesn't depend on IPs.

## Security

| Threat | Prevention |
| --- | --- |
| The link leaks (server logs, BrowserStack logs and screenshots, chat, history, Referer). | Key required by default; key sent separately; short expiry; single use; the token is removed from the URL after entry; `Referrer-Policy: no-referrer`; revocation. |
| Key guessing. | Generated keys have about 48 bits of entropy (10 characters from 29); the link locks after 5 failures; per-IP rate limit; custom keys need 8+ characters. |
| Token guessing. | 256-bit random tokens; only HMAC hashes stored; lookup by hash. |
| Probing whether a link is valid. | Identical form on GET; identical message for every failure; dummy hash so timing is the same. |
| Link scanners or unfurlers spending or locking links. | GET reads and spends nothing; only POST does. |
| Double spend (double click, two tabs, replay). | Single conditional `UPDATE`, granted only with exactly one affected row. |
| CSRF on the key form or End preview. | Double-submit cookie (`SameSite=Strict`) compared with `hash_equals()`. Impact would be low anyway: loading a preview in a victim's browser. |
| Tampered toolbar pre-fill (`tt_share_theme`, `tt_share_path`), for example a link that pre-fills a foreign URL. | Pre-fill only suggests: the theme must be in the user's shareable themes, the path is reduced to a same-site path and validated again on submit, and opening the form changes nothing. |
| Session cookie theft. | `HttpOnly`, `Secure`, never in a URL, only a hash stored, lives no longer than the link, revocable. It grants only a theme view. |
| Privilege escalation through the link. | No login; `wp_set_current_user()` is never called; no capabilities; front end only. |
| The link outlives the creator's permission. | Creator, share role and `can_user_select()` checked on every request. |
| A broken or unpermitted theme shown to the public. | Normal validation (invariant 11); only the creator's permitted themes can be shared. |
| Theme code exposed to anonymous visitors (unfinished themes, debug output). | Admin opt-in; only permitted themes; recommend using it on staging. |
| Clickjacking of the key form. | `X-Frame-Options: DENY` (and `Content-Security-Policy: frame-ancestors 'none'`). |
| Key shown or stored in plain text. | Hashed with `wp_hash_password()`; shown once from a 5-minute transient; never in URLs, logs or the admin list. |
| Abuse of creation (spam links). | Nonce, capability, role check, active-link limit. |
| Spoofed IP to bypass the rate limit. | `REMOTE_ADDR` only, unless a proxy header is configured. |
| XSS in the key form, the preview bar or the lists. | All output escaped; theme names through `esc_html()`. |

## Caching and headers

This is the largest practical risk. Anonymous visitors are exactly the traffic page caches and CDNs store.

1. **Cache poisoning:** a page rendered for a share visitor is cached and served to everyone. Every share response is private, no-store, no-cache with `Vary: Cookie`, `DONOTCACHEPAGE` and TTF010's signals.
2. **Stale default page:** a share visitor gets a cached default page. This needs the cache to **bypass** on the `wp-themetoggle-share` cookie. Document the rule for each cache in the README, and warn in Site Health (TTF010) if a page cache is active and the bypass can't be confirmed.
3. **The key form page** is `no-store`: a cached form would carry an old anti-CSRF value.
4. **CDNs that ignore `Vary`:** rely on `CDN-Cache-Control: no-store` and the cookie bypass rule.

For these reasons TTF010 is a prerequisite.

## Data integrity, privacy and leakage

- **No user data reaches the visitor:** the bar shows the theme name only; error pages say nothing about the creator or the link.
- **Site content:** the visitor sees the public site as any anonymous visitor would. No private posts or drafts.
- **Real actions:** forms, comments and checkout on the previewed site do real things. Say so in the bar and recommend staging.
- **IP addresses** are personal data: only salted hashes, only in rate-limit transients (15 minutes), never in the tables.
- **Privacy policy text:** `wp_add_privacy_policy_content()` describes the cookie, the retention and what is stored.
- **Personal data exporter** for creators: their links (theme, dates, status), never keys or tokens.
- **Server logs** will contain the first GET URL with the token. That can't be avoided; the key, the single use and the expiry make a logged token useless.
- **Data_Guard:** theme mods go to the shared theme's row; `sidebars_widgets` is not written.

## Performance

- **Requests without the cookie:** one `isset( $_COOKIE[…] )` check; no cost for normal visitors.
- **Requests with the cookie:** one indexed query per request, cached for the request.
- **POST:** a few queries and one password hash check, which is slow by design (that is the point).

## Compatibility

- PHP 7.4: `setcookie()` with an options array (SameSite support).
- WordPress 5.9+: everything used exists.
- SQLite integration (e2e): check the `CREATE TABLE` from `dbDelta()` and the conditional `UPDATE` there.
- Subdirectory multisite: `COOKIEPATH` per site keeps the cookie on the right site.
- Some managed hosts with forced edge caches may not allow cookie bypass. The feature must say "not supported here" when Site Health can't confirm a bypass.

## Architecture invariants

| Invariant | How it stays true |
| --- | --- |
| 1. Never write `template` / `stylesheet` or call `switch_theme()`. | Theme applied through the existing filters only. |
| 2. No `wp_get_theme()` without an argument on the resolution path. | `Share_Session` uses `Theme_Manager::get_theme( $slug )`. |
| 3. A saved value is not permission. | The creator's permission is checked on every request. |
| 5. Nonce and capability on state changes. | Nonces for logged-in handlers; double-submit cookies for the two anonymous handlers (nonces can't work there); capability or creator checks on revoke. The ARCHITECTURE.md security table needs rows for the first `nopriv` handlers. |
| 6. `Data_Guard` active. | Activates whenever a theme is applied. |
| 7. Never publicly cacheable. | Headers above plus TTF010. |
| 11. Filter and supplied themes validated; never in context `none`. | Share branch only in `frontend` context; normal validation. |

## Tests

Add to `tests/e2e/http-tests.sh`, using a cookie jar per "browser". Names start with `TTF018`.

### Creating

- Feature off: create refused; the profile shows no section.
- A user not in `share_roles`: refused.
- A non-permitted theme (forged POST): refused.
- The 6th active link with limit 5: refused.
- Minutes and uses above the maximum: clamped.
- The link and key appear once; reloading the page doesn't show them again; neither appears in any URL or redirect `Location` header.
- The database holds no plain token or key: search `tt_share_links` for the token and key strings and find nothing.

### Toolbar (with TTF001)

- A user allowed to share sees `wp-admin-bar-themetoggle-share-create` and `wp-admin-bar-themetoggle-share-list`; a user not in `share_roles`, or with the feature off, sees neither.
- "Share this page…" on `/sample-page/` while on `tt-child`: the form opens with `tt-child` selected and the path `/sample-page/`.
- Opening the pre-fill URL creates no link (row count in `tt_share_links` unchanged).
- `tt_share_theme` set to a non-shareable theme: the select starts at the first shareable theme. `tt_share_path=https://evil.example/x`: the path field holds no foreign host, and a submit with it ends on the site.
- "My preview links (2 active)" shows the right count after creating two links and revoking a third.

### Opening

- GET with a valid token and GET with a random token: byte-identical HTML apart from the form cookie value; status 200; headers `no-store`, `noindex`, `no-referrer`, `X-Frame-Options`.
- GET doesn't change `uses_left`, `failed_attempts` or `last_used_at`.
- POST without the form cookie, or with a mismatched one: refused; nothing changed.
- A wrong key: generic message; `failed_attempts` +1; `uses_left` unchanged.
- 5 wrong keys: status `locked`; then even the correct key is refused.
- 11 failures from one IP across different links: the 11th is rate-limited.
- Correct key: 303 to a URL without `tt_share`; the share cookie is set with `HttpOnly` and `SameSite=Lax`; `uses_left` −1.
- A 1-use link opened a second time from a new cookie jar: refused.
- A 3-use link: works in exactly 3 cookie jars; the 4th is refused.
- Two POSTs at the same moment on a 1-use link (two `curl` calls in the background): exactly one success.
- An expired link (set `expires_at` in the past through WP-CLI): refused.

### Browsing

- With the cookie: every front-end page uses the theme (`tt-functions-*` marker); `Cache-Control` has `private` and `no-store`; `Vary: Cookie`; `noindex`.
- With the cookie on `/wp-admin/` and on an excluded page: no share theme; the visitor isn't logged in.
- A logged-in user with a share cookie: their own rules apply.
- Revoke: the next request with the cookie gets the default theme and the cookie is expired.
- The creator loses the theme from their role, or the creator is deleted: the default theme on the next request.
- The feature is turned off: the default theme.
- A tampered cookie value: the default theme.
- `theme_mods_{default}` and `sidebars_widgets` unchanged after share requests that call `set_theme_mod()` (e2e mu-plugin switch).
- End preview: POST with the form cookie deletes the session; without it, refused.

### Cleanup

- A link that ended 31 days ago with retention 30: deleted by `wp cron event run themetoggle_share_cleanup`; a link that ended 29 days ago is kept.
- Deactivation unschedules the event; uninstall drops both tables.

1. Should admins be able to create links for themes outside their own permitted list (for example any installed theme)? Recommendation: no; keep "only your permitted themes", and admins can permit themselves more.
2. Should links be allowed on production at all, or only when `wp_get_environment_type()` is `staging` or `development`? Recommendation: allowed everywhere, with a warning on production.
3. Should link events go to the audit log (TTF011) when it exists? Recommendation: yes: created, opened, locked and revoked.
